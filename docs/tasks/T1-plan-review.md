# T1：NetSuck 规划与契约独立审查（规划把关，不写代码）

你是本项目的独立规划审查员。仓库位于 `/Users/strom/Repositories/GitHub/NetSuck`（已信任）。

## 输入
1. `docs/SPEC.md` —— 项目需求规格（唯一需求来源，逐条为准）
2. `docs/PLAN.md` —— 协调者制定的开发编排计划：任务 DAG、全局工程约定、以及跨 worker 的契约（Go 类型契约 §3、数据库契约 §4、引擎契约 §5、REST API JSON 契约 §6、基础设施契约 §7、协调者决策记录 §9）

## 背景
后续实现将由多个不同模型的 worker 分工完成（config.go / db.go / engine.go / main.go / web/index.html / Docker&CI 由不同人写），他们之间**只靠 PLAN.md 的契约对齐**，无法互相商量。因此契约中的任何歧义、遗漏、类型不一致，都会直接变成线上 bug。你的审查是实施前的最后一道关口。

## 审查维度（按优先级）
1. **契约可实现性与一致性**：PLAN §3-§6 中的 Go 结构体、DB 表、REST JSON 字段名/类型/取值范围是否互相一致、是否足以支撑 SPEC 全部需求、有没有字段缺失（例如前端需要的某数据 API 没给）或语义歧义（例如跨夜 schedule 的边界、`cooldown_remaining_seconds` 的计算基准）。
2. **并发设计风险**：PLAN §5 引擎契约的 12 条机制在并发正确性上是否有漏洞（动态 worker 池与 host 互斥的交互、原子计数与刷盘的一致性、SetMaxConnections 平滑增减的竞态、速率采样的并发读、热更新与下载循环的交互）。
3. **SPEC 覆盖度**：将 SPEC §3（3.1/3.2/3.3 每一条）、§4、§5 的每一条要求与 PLAN 契约逐一对照，列出任何未被契约覆盖或被弱化的需求。
4. **协调者决策裁决**：对 PLAN §9 的 D1-D6 逐条给出 同意/反对+理由。
5. **任务 DAG 合理性**：依赖顺序是否正确、审查是否覆盖了每个实现块。

```
【发现清单】（按严重度排序；没有就写"无"）

...

【决策裁决】D1: 同意/反对（理由）... D6: ...

【SPEC 覆盖度】逐条核对结果，仅列出有问题的条目
```
